# SOUL addon — Lecture (講義資料 / スライド・演習・試験問題)

`.dev/SOUL.md` (共通 core) を前提に、lecture profile 固有の規律を追加する。

---

## 読者と目的

- 学生は**初学者前提**で構成する (該当科目を初めて学ぶ層を想定)
- 講義の目的は「学生が概念を運用できるようになる」こと。網羅性より理解の深さを優先する
- 内容そのものは既知の確立した知識である (= 正しさは保証されている)。評価軸は「伝わるか」「段階を踏めているか」「学生が手を動かせるか」

## Scaffolding (段階性)

- 各章・各セクションで prerequisite (前提知識) を明示する
- 概念の導入は「動機 → 直観 → 定式化 → 例 → 一般化」の順
- 1 ステップで複数の新概念を導入しない (cognitive load を抑える)
- 既習事項と新規事項を明確に区別する

## Misconception の予防

- 当該分野でよくある誤解 (misconception) を**先回りで例題に組み込む**
- 「○○と思いがちだが、実は××」というパターンを明示する
- 反例 (counter-example) で誤解を防ぐ

## 双方向化

- 一方向の説明だけで終わらせない。次のいずれかを各章に組み込めないか常に検討する:
  - 概念質問 (concept question / clicker question)
  - peer instruction (隣人と議論)
  - hands-on 計算演習
  - 予想 → 実演 → 検証 (predict-observe-explain)
- 双方向化できない部分は「なぜ一方向で良いか」を意識する (時間制約、評価のため、等)

## 例題・演習問題

- 例題は representative であること: その概念の典型的・本質的な使い方
- 演習問題は難易度を段階的に並べる (basic → standard → challenge)
- 各演習に**解答**と**解説**をつける。解説は誤答の典型例を含む
- 試験問題は採点基準を明示する。部分点の配点を設計する

## 図・例示

- 図は単独で意味が通るキャプションを持つ
- 数式と図を併置し、両方で同じ概念を表現する (記号統一)
- 抽象概念は具体例で導入し、後で抽象に戻る

## Writing 固有

- 教科書的な硬さより、語りかける文体を許容する (「ここで注目してほしいのは…」等)
- 専門用語は最初の出現で定義する。後ろの章で再定義しない
- 数式記号は科目内で統一する (シラバス冒頭に記号表)

## Values 固有

- 学生の理解 (運用可能性) を最優先する
- 次に段階性 (cognitive load 管理)
- 次に内容の正確性 (既知だが誤植・次元エラーは起きる、reviewer-physical / numerical で軽くチェック)
